# 按需执行协议

## 接入与范围

先查实际项目入口、构建/测试命令、CI 和模块边界，复用已有机制。只补本轮必需的资料，未知命令写未配置，不照搬 Magpie 平台或技术栈。

普通任务用一段记录即可：目标与来源、影响范围、验收行为、必须保持的决定、验证结果和剩余问题。多人交接时再补负责人、分支/工作区、基线与变更 SHA、依赖和状态；不为独立小改建立任务管理系统。

## 顺序完成三个职责

1. 实现：复现问题，沿实际调用链找根因，检查同类路径，做最小相关修复和适当回归。
2. 独立审查：需要合并时交新的会话或另一审查者；独立读需求、产品决定、diff 与证据，不只复述作者解释。普通本地小改允许轻量自检，但必须明确尚未独立审查。
3. 验证交付：按风险执行检查、记录实际受测状态。主线变更、合并或发布须满足对应项目门槛及授权；其余任务交付本地结果后结束。

完成当前目标、需要人的决定、缺关键环境，或达到约定预算时保存检查点并停止。同一失败两次没有新证据就停止盲目重试，写明下一项有信息增益的检查。不要自动领取新任务，不靠削减必需验证来伪装完成；预算不足就交付待审或阻塞结果。

## 一致性与协作

DECISIONS.md 只记录影响产品行为、模块边界、数据所有权或稳定接口的重要决定，不记录日常编码选择。改动推翻既有决定时说明新理由与影响，涉及负责人产品取舍先取得决定；更新原记录状态并链接替代项，避免两份有效规则互相冲突。

模块说明明确谁拥有状态、谁调用谁、输入输出与不变量。实现与文档不一致时先查清事实再同步；不让 agent 默默按过时文档扩散错误。

仅在任务确实可独立且并发收益值得成本时考虑并行，并遵循环境的 delegation 授权。并行者使用隔离分支和工作区，单一集成人收口，不提交他人未提交修改。串行任务无需为每个步骤新建工作区；回退、破坏测试使用隔离副本。

## 反馈与 UI 验收

只处理本轮相关、已可访问的反馈，保留来源与最新上下文，去重后转成验收行为；不常驻抓取社区。产品建议不等于已批准决定，发送回复仍需授权。

UI 任务提供可使用的候选版本和操作路径；按改动检查正常、空、加载、错误等相关状态。必要演示数据隔离且标明为合成；截图不能替代真实性能或集成证据。人工在阶段交付时判断体验即可，不要求每晚巡视。

## 仅在合并时

审查与检查记录绑定 head、基线及整合候选 SHA；内容或基线变化后重验受影响保证。GitHub 可用 `gh pr merge --match-head-commit <reviewed-head-sha>` 防 head 漂移，但它不锁 base；以串行集成、merge queue 或项目现有保护保证最终结果。发布另读验收规则，不因小改机械发版。
